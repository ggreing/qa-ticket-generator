# qa-ticket-generator 기획서 v3 (재설계: 기획서 기반 QA 케이스 티켓)

| 항목      | 내용                                                                                                                                                         |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 문서 버전 | v3.1 (2026-11-13)                                                                                                                                            |
| 상태      | **승인, 구현 완료(R0–R2, 샌드박스 E2E)**. 공개 준비 중                                                                                                       |
| 관계      | v2(`docs/SPEC.ko.md`)를 대체하는 부분만 적는다. 여기 없는 내용(PRD 수집 규약, 비밀값 마스킹, 비용 가드, 보안 모델, i18n, 평가 하네스 구조)은 v2를 따른다     |

---

## 1. 제품 재정의

> **기획서(명세서)를 읽고 QA가 수행해야 할 테스트 케이스를 빠짐없이 도출해 케이스마다 티켓으로 만들고, PR이 올라오면 코드와 대조해 각 케이스의 구현 상태를 갱신하고, 코드에서만 보이는 위험을 케이스로 추가하는 도구.**

|           | v2 (현재 구현)    | v3                                                                                                 |
| --------- | ----------------- | -------------------------------------------------------------------------------------------------- |
| 출발점    | PR 코드 변경      | **기획서** (+ PR 시점에 코드)                                                                      |
| 목표      | 머지 전 위험 점검 | **놓치기 쉬운 케이스까지 전부** QA 항목화                                                          |
| 분량      | 간결하게 8개 이하 | **전부**, 우선순위로 정렬 (안전 상한만 둠)                                                         |
| 결과물    | PR 코멘트 1개     | **케이스별 티켓** (Jira 하위 작업, GitHub Issue, Notion DB 행, CSV/Markdown 파일) + PR 요약 코멘트 |
| 사람 기록 | 없음              | QA의 실행 결과·담당자·코멘트를 **절대 덮어쓰지 않음**                                              |

## 2. 두 단계 동작

### 2.1 기획 단계 (Plan)

| 항목   | 내용                                                                                                                                                                                                                                                         |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 트리거 | ① 기획서가 GitHub Issue: 라벨 `needs-qa-plan` 부착 시 자동 ② Jira/Notion 기획서: Actions 수동 실행(`spec` 입력에 링크·키) 또는 CLI `qa-ticket-generator plan --spec PROJ-123` ③ Jira 자동화(상태 변경 시 `repository_dispatch` 호출) 연동 방법은 문서로 제공 |
| 입력   | 기획서 본문, 인수 조건(AC), 기획서 안의 링크 문서(v2 PRD 규약), 레포 설정의 도메인 설명                                                                                                                                                                      |
| 처리   | AC마다 적용 가능한 **테스트 기법**을 모두 검토해 케이스 도출 → 중복 병합 → 우선순위 부여 → 기존 케이스와 대조(§4) → 내보내기                                                                                                                                 |
| 출력   | 케이스 티켓 세트, 기획서 쪽 요약(GitHub Issue면 코멘트, Jira면 스토리 코멘트), Job Summary                                                                                                                                                                   |

### 2.2 구현 단계 (Verify, PR)

| 항목   | 내용                                                                                                                                                                                                                                                                        |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 트리거 | v2와 같음: PR 라벨 `needs-ai-qa`, 라벨 유지 중 push 재실행                                                                                                                                                                                                                  |
| 입력   | PR diff(+ 함수 단위 컨텍스트), PR 본문의 기획서 링크, **그 기획서의 기존 케이스 세트**(내보낸 곳에서 읽음. 없으면 기획 단계를 먼저 수행)                                                                                                                                    |
| 처리   | ① 케이스마다 **코드 상태** 판정: `구현 확인됨` / `미구현 의심` / `기획과 상충` / `코드로 판단 불가` (근거 파일·함수 기록) ② 기획서에 없지만 diff에서 보이는 위험을 **코드 출처 케이스**로 추가(권한, 부분 실패, 하위 호환 등 v2 점검표) ③ 요구사항 정합성(v2 findings) 유지 |
| 출력   | 케이스 티켓의 코드 상태 갱신, 새 코드 출처 케이스 티켓, **PR 요약 코멘트**(정합성 배지, 상태별 건수, 미구현·상충 케이스 링크, P0 체크리스트)                                                                                                                                |

## 3. 케이스 모델 (`QaCase`)

| 필드                                             | 설명                                                                                                                                               | 소유                                         |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| `caseId`                                         | 안정적인 ID (예: `PROJ-123-C07`). 재실행해도 같은 케이스는 같은 ID                                                                                 | 도구                                         |
| `title`                                          | `[P0] 만료 1초 지난 쿠폰 거부` 형식의 한 줄                                                                                                        | 도구                                         |
| `specRef`, `acLabels`                            | 출처 기획서, 관련 AC(복수 가능). 코드 출처 케이스는 AC 없이 코드 위치                                                                              | 도구                                         |
| `technique`                                      | 정상 흐름 / 경계값 / 동등 분할 / 잘못된 입력 / 상태 전이 / 권한 / 동시성 / 실패·타임아웃 / 중복·멱등성 / 하위 호환 / 시간대·로케일 / 데이터 정합성 | 도구                                         |
| `priority`                                       | P0(데이터 손실, 금전, 보안, 핵심 흐름) / P1 / P2                                                                                                   | 도구                                         |
| `preconditions`, `testData`, `steps`, `expected` | 바로 실행 가능한 수준으로 구체적. `expected` 첫 줄 = 합격 판정 기준                                                                                | 도구                                         |
| `whyEasyToMiss`                                  | 기획서에 무엇이 빠져 있어 놓치기 쉬운지 한두 문장                                                                                                  | 도구                                         |
| `origin`                                         | `spec` / `code`                                                                                                                                    | 도구                                         |
| `codeStatus`                                     | 구현 단계 판정 결과와 근거(파일·함수), 판정한 커밋 SHA                                                                                             | 도구                                         |
| `lifecycle`                                      | `active` / `obsolete`(기획에서 빠짐, 닫지 않고 표시)                                                                                               | 도구                                         |
| **실행 결과·담당자·코멘트**                      | 미실행 / Pass / Fail / Blocked, 담당자, 토론                                                                                                       | **QA(사람)**. 도구는 읽기만 하고 쓰지 않는다 |

### 3.1 문체: 실제 QA 목록처럼 (AI스럽지 않게)

케이스 텍스트는 현업 QA 담당자가 테스트 케이스 시트에 적는 말투를 따른다. 사람이 읽고 바로 손을 움직일 수 있어야 하고, 설명하거나 설득하는 글이 아니다.

| 규칙                                           | 실제 QA 목록 (O)                                       | AI스러운 표현 (X)                                                                                                                                        |
| ---------------------------------------------- | ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 제목은 "대상 + 조건 + 결과"의 짧은 명사구      | `만료 1초 지난 쿠폰 적용 시 거부`                      | `만료된 쿠폰이 올바르게 거부되는지 확인하는 테스트`                                                                                                      |
| 단계는 동작만 짧게, 번호로                     | `1. 결제 화면 진입` `2. 쿠폰 EXP1 입력 후 적용`        | `먼저 사용자는 결제 화면으로 이동해야 합니다`                                                                                                            |
| 기대 결과는 관찰 가능한 사실                   | `"만료된 쿠폰입니다" 토스트 노출, 결제 금액 변화 없음` | `시스템이 적절하게 오류를 처리해야 합니다`                                                                                                               |
| 데이터는 실제 값                               | `쿠폰 EXP1 / 만료 2026-11-13 23:59:59 / 주문 30,000원` | `유효하지 않은 쿠폰 데이터`                                                                                                                              |
| 금지 표현                                      |                                                        | "\~를 보장", "\~를 검증합니다", "적절히/올바르게/원활하게", "\~할 수 있어야 합니다", "이 테스트는", 대시(—)로 덧붙이는 설명, 콜론 뒤에 반전 제시, 이모지 |
| 우선순위·기법은 라벨로만                       | `[P0] [경계값]`                                        | 본문에서 "이것은 매우 중요한 경계값 테스트입니다"                                                                                                        |
| 왜 필요한가(`whyEasyToMiss`)는 한 문장, 사실만 | `기획서에 만료 시각 포함 여부(이하/미만) 정의 없음`    | `이 케이스는 개발자가 놓치기 쉬운 중요한 경계 조건을 다룹니다`                                                                                           |

- 언어별로 그 언어 QA 현장의 관용을 따른다. 한국어는 개조식(`~시 ~됨`, `~노출`, `~불가`)과 명사형 종결을 쓰고, 영어는 명령형 단계와 짧은 기대 결과를 쓴다.
- 팀마다 쓰는 말이 다르므로 레포 설정에 **문체 예시**(`prompt.styleExamples`: 기존 QA 케이스 몇 줄)를 넣을 수 있게 한다. 있으면 그 말투와 용어를 우선한다.
- 품질 확인: (1) 금지 표현 목록을 코드로 검사한다(결정적 지표 "AI 문체 위반 수"). (2) 루브릭에 **"QA 목록다운 문체"** 기준을 추가한다(0: 설명조·AI 상투어, 1: 일부 설명조, 2: 현업 QA 시트와 구분이 안 됨). (3) 사용자 평가에서 따로 묻는다.

## 4. 재실행과 동기화 규칙

1. **같은 케이스 판단**: 재생성 시 기존 케이스 목록(ID, 제목, AC, 기법)을 모델에 함께 주고 "같은 테스트 의도면 기존 ID를 재사용"하게 한다. 코드에서 ID 중복·형식을 검증하고, 애매하면 새 ID로 둔다(중복보다는 새 케이스가 안전).
2. **갱신**: 도구 소유 필드만 갱신한다. 사람 소유 필드(실행 결과, 담당자, 코멘트, 사람이 단 라벨)는 건드리지 않는다.
3. **추가**: 새 케이스는 새 티켓으로 만든다.
4. **빠진 케이스**: 지우거나 닫지 않고 `obsolete`로 표시하고, 제목 앞에 `[해당 없음]`을 붙인다. 단, 코드 출처(`origin: code`) 케이스는 기획 재실행으로 obsolete가 되지 않고, 구현 단계에서만 판단한다. 기획서가 그 위험을 흡수해 같은 ID를 재사용하면 기획 출처로 바뀐다.
5. **사람이 수정한 본문**: 도구가 마지막으로 쓴 내용의 해시를 티켓의 숨김 영역에 저장한다. 사람이 본문을 고쳤으면 덮어쓰지 않고 "도구 제안 변경"을 코멘트로 남긴다.
6. **표식**: 모든 케이스 티켓에 `qtg-case:<caseId>` 표식을 둔다(라벨이나 속성, 숨김 주석). 이 표식으로 기존 티켓을 찾는다. 별도 서버나 DB는 없다(v2의 Stateless 원칙 유지).

## 5. 내보내기 (`CaseSink`)

| 대상             | 형태                                                                       | 표식                            | 사람 소유 상태                                | 인증                                                                           |
| ---------------- | -------------------------------------------------------------------------- | ------------------------------- | --------------------------------------------- | ------------------------------------------------------------------------------ |
| **Jira**         | 기획 스토리의 **하위 작업(Sub-task)**                                      | 라벨 `qtg-case`, `qtg-<caseId>` | Jira 이슈 상태, 담당자                        | 기존 Jira input + 쓰기 권한                                                    |
| **GitHub Issue** | 케이스마다 이슈. 기획 이슈에 케이스 목록 코멘트(체크리스트, 갱신형)        | 라벨 `qa-case`, 본문 숨김 주석  | open/closed, 라벨 `qa:pass`·`qa:fail`, 담당자 | `issues: write`                                                                |
| **Notion**       | 지정한 QA 케이스 데이터베이스의 행                                         | `Case ID` 속성                  | `실행 결과`, `담당자` 속성                    | `notion-token` + `notion-qa-database-id`(속성이 없으면 첫 실행 때 만들기 시도) |
| **파일**         | `qa-cases.md`(사람이 읽는 표)와 `qa-cases.csv`(TestRail·스프레드시트용 열) | 열 `case_id`                    | (파일이므로 없음)                             | 없음. Action에서는 아티팩트로 업로드                                           |

- 여러 곳을 동시에 켤 수 있다. 각 대상은 독립적으로 실패한다(v2 DLV-08 원칙).
- 기존 케이스 세트를 읽어 올 **기준 대상**은 우선순위 Jira > Notion > GitHub Issue 순서로 하나를 쓴다. 파일만 쓰는 경우에는 이전 실행의 `qa-cases.json`을 입력으로 받는다.

## 6. 분량과 비용

- **빠짐없이**: AC × 적용 가능한 기법을 모두 검토한다. 기획서 하나에서 20\~60개 정도를 예상한다.
- **안전 상한** `max-cases`(기본 80)와 비용 상한 `max-cost-usd`(기본 $2, v2와 같음)를 둔다. 상한에 걸리면 P2부터 생략하고 생략 사실을 요약에 적는다.
- 출력이 길어지므로 AC 묶음 단위로 나눠 생성한 뒤 병합한다(중복 제거와 우선순위 재조정).
- 예상 비용(추정): 기획 단계는 기획서당 $0.5\~2, 구현 단계는 PR당 $0.2\~0.5(v2 수준). 첫 실측으로 갱신한다.
- v2의 `max-scenarios`(PR 코멘트 상한 8)는 **PR 요약 코멘트에 보여 줄 P0 체크리스트 개수**로 의미를 바꾼다. 케이스 생성 개수와는 무관하다.

## 8. 품질 기준 변경 (루브릭 v3)

| 기준                                       | 단위   | v2 대비                                                |
| ------------------------------------------ | ------ | ------------------------------------------------------ |
| 실행 가능성, 근거 연결, 우선순위           | 케이스 | 유지                                                   |
| **놓치기 쉬운 케이스 가치** (구 위험 적중) | 케이스 | "사람이 기획서만 보고 놓칠 만한가"를 본다              |
| **기획 커버리지**                          | 기획서 | AC × 해당 기법을 빠짐없이 다뤘는가. 가장 중요한 기준   |
| **중복 없음** (구 간결성)                  | 기획서 | 길이는 벌하지 않는다. 같은 테스트 의도의 중복만 벌한다 |
| 정직성                                     | 기획서 | 유지                                                   |
| **QA 목록다운 문체**                       | 케이스 | 신규(§3.1). 금지 표현 코드 검사와 함께 본다            |
| **코드 상태 판정 정확도**                  | PR     | 구현 단계. 정답이 있는 케이스는 결정적 채점            |

- 평가 세트: 기존 합성 25건의 기획서와 정답을 재사용한다. 정답에 "반드시 나와야 할 케이스"를 위험 단위로 보강하고, 코드 상태 정답을 추가한다.
- 사람 평가: 개발 후 한국어 출력으로 사용자 평가를 받는다(M3.5와 같은 방식).

## 9. 아키텍처 변경 요약

- core 계약: `QaCase`, `CaseSet`, `CaseSink`(list / create / update / markObsolete), `Mode`. `QaReport`는 구현 단계 PR 요약에만 남긴다.
- 파이프라인: `runPlan()`과 `runVerify()` 두 진입점. 공통 단계(PRD 수집, 마스킹, 비용 가드)는 공유한다.
- 새 모듈: `src/cases/`(동기화 엔진: ID 대조, 소유 필드 병합, obsolete 처리, 사람 수정 감지), `src/sinks/`(jira, github-issue, notion, file).
- LLM: 기획 단계 생성(AC 묶음별 + 병합), 구현 단계 판정(케이스별 코드 상태 + 코드 출처 케이스). 프롬프트는 M3.5의 개선(구체적 데이터, 합격 판정 줄 먼저, 위험 점검표, 부분 구현 규칙)을 계승한다.
- 재사용: PRD 수집 3종, 전처리 엔진(Rust 전환점), 비밀값 마스킹, 비용 가드, 트리거·설정·어댑터 구조, 평가 하네스, 보안 모델.

## 13. 구현 중 확정된 규칙 (v3.1, 2026-11-13)

평가 2라운드와 샌드박스 E2E에서 드러난 문제를 사용자 결정으로 정한 규칙이다.

| 영역    | 규칙                                                                                                                                                                                                                                | 이유                                       |
| ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| 생성    | 의도 하나에 케이스 하나. 같은 종류의 다른 값은 테스트 데이터에 나열하고, 경계값의 통과 쪽과 실패 쪽은 따로 둔다. 공통 상황(중복 전송, 의존 서비스 장애)은 관련 AC를 모두 적은 케이스 하나로 쓴다                                    | round 0의 중복(중복 없음 0.57/2)           |
| 생성    | 기획서가 정하지 않은 결과는 확정하지 않고 `기획 확인 필요:` 줄로 남긴다. 기획서에 명시된 기본 흐름은 `whyEasyToMiss`를 비운다                                                                                                       | round 0 정직성 1.43 → round 1 1.86         |
| 생성    | 비슷한 케이스 병합은 전제 조건·데이터까지 보고, 이유를 쓰지 못하면 지우지 않는다                                                                                                                                                    | 상태가 다른 케이스를 지운 오판             |
| 재실행  | 기획서 내용(digest)이 지난 plan과 같으면 생성을 건너뛴다. 사람이 고친 티켓은 비교에서 뺀다. `force-plan`으로 강제한다. 건너뛸 때도 파일(CSV/MD/JSON)은 다시 쓴다                                                                    | 같은 기획서 재실행으로 55→64건 증가        |
| 재실행  | 이미 대조한 커밋은 다시 대조하지 않는다(수동 실행 제외)                                                                                                                                                                             | 같은 커밋 재대조로 표현만 바뀐 케이스 증가 |
| 대조    | 새 케이스는 기존 케이스 전체 색인을 보고, 같은 위험이면 `sameAsCaseId`로 기존 케이스를 가리켜 버린다. 코드에도 표현만 다른 제목을 걸러내는 안전망이 있다                                                                            | 재대조 중복                                |
| 대조    | 첫 대조 이후에는 지난 대조 이후 바뀐 줄이 만든 위험만 새 케이스로 만든다. 주석·포매팅만 바뀐 push는 대조 자체를 건너뛴다(판정 없는 케이스가 있으면 그것만 판정)                                                                     | 주석 한 줄 push로 6건 증가                 |
| 대조    | 첫 대조 이후에는 판정이 없는 케이스, 근거 파일이 동작을 바꾼 케이스, 이전에 missing·unknown이던 케이스만 다시 판정하고 나머지는 이전 판정을 유지한다                                                                                | 같은 코드에서 판정 흔들림(상충 3→10)       |
| 대조    | 요구사항 판정: 충족(기본 동작 있음, 케이스에 missing·contradicts 없음) / 부분 충족(기본 동작 있음, 일부 케이스 missing·contradicts) / 누락(기본 동작 없음) / 상충(기본 동작이 반대). 모델 판정을 케이스 판정에 맞춰 코드가 확정한다 | 가장자리 하나로 "누락"이 되던 문제         |
| 대조    | 새 케이스 범위의 diff도 노이즈 경로를 빼고 비밀값을 한 번 가린다. 가린 건수는 PR 요약에 표시한다                                                                                                                                    | PRE-05                                     |
| 동기화  | 내용이 같고 내부 기록만 바뀐 갱신은 본문을 다시 쓰지 않는다(GitHub: 숨김 주석만, Jira: issue property, Notion: 속성만)                                                                                                              | Jira 알림 폭주 방지                        |
| 동기화  | 링크가 없는 sink(file)가 다른 sink의 티켓 링크를 덮어쓰지 않는다                                                                                                                                                                    | 기획서 목록에 링크 누락                    |
| fail-on | `misaligned`는 요구사항 기본 동작이 기획과 반대일 때만 걸린다. 가장자리 케이스까지 막으려면 `partial`                                                                                                                               | 위 요구사항 판정 규칙의 결과               |
